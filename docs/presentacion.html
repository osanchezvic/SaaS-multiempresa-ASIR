01 El problema

Dar de alta un cliente
es lento, manual y frágil.

Cómo se hace hoy
  • Instalación manual servicio por servicio
  • Proxy y certificados SSL configurados a mano
  • Puertos abiertos al exterior = superficie de ataque
  • Datos de clientes mezclados, sin aislamiento claro
  • Cada alta = horas de trabajo no reproducible
Lo que necesitamos
  • Alta de un servicio en segundos, repetible
  • Proxy + SSL + SSO automáticos
  • El host no publica ningún puerto
  • Cada cliente aislado en red, datos y secretos
  • Todo registrado y auditable
02 La solución

Infraestructura SaaS
multi-tenant como producto.

Un orquestador en Bash sobre Docker que automatiza el ciclo completo de un servicio para un cliente. Se asienta en tres principios.

PRINCIPIO 01

Soberanía del dato

Cada tenant aislado en red, almacenamiento físico y secretos propios.

PRINCIPIO 02

Zero-Exposure

El host no abre ni un puerto al exterior. Todo entra por túnel saliente.

PRINCIPIO 03

Automatización total

Un comando: servicio, proxy, SSL y SSO listos y registrados.

03 Objetivos

Qué tenía que conseguir

  • Despliegue de un solo comando que resuelva dependencias entre servicios (ej. WordPress trae su MariaDB y su Redis).
  • Aislamiento multi-tenant real a nivel de red Docker, rutas de datos y credenciales por empresa.
  • Perímetro sin puertos expuestos, con acceso unificado por SSO y doble factor.
  • Catálogo extensible de servicios mediante plantillas, sin tocar el motor.
  • Observabilidad y alertas desde el día uno (métricas + avisos a Telegram).
  • Estado siempre coherente: reconciliación automática registro ↔ realidad.

05 Pilar 1 · Zero-Exposure

El servidor no se ve
desde Internet.

En vez de abrir puertos y filtrarlos, el host no publica ninguno. Es él quien abre una conexión saliente a Cloudflare; todo el tráfico vuelve por ese túnel cifrado.

  • Un nmap a la IP no encuentra superficie de ataque.
  • DDoS, WAF y TLS los absorbe Cloudflare, no el servidor.
  • Administración interna solo por túnel SSH.
nmap tensaas.es
# Escaneo desde fuera del perímetro
$ nmap -Pn -p- tensaas.es

Host is up.
All 65535 scanned ports are filtered

# No hay nada que atacar. El tráfico
# legítimo entra así:
Usuario → Cloudflare → túnel ↑ → NPM → tenant

06 Pilar 2 · Soberanía del dato

Cada cliente, en su propia burbuja

CAPA · RED

Aislamiento de red

Una bridge Docker empresa_net por tenant. Los contenedores de un cliente no ven a los de otro.

CAPA · DISCO

Datos separados

Ruta física propia /data/<empresa>/<servicio>. Backup, borrado y migración por cliente.

CAPA · SECRETOS

Credenciales propias

Generadas con openssl, guardadas en JSON chmod 600. Nunca compartidas entre tenants.

El aislamiento no es una promesa de configuración: está impuesto por Docker a nivel de kernel (namespaces de red) y por el sistema de ficheros.
07 Pilar 3 · Automatización total

Un comando.
Todo lo demás, solo.

  • flock evita despliegues concurrentes que se pisen.
  • Resuelve dependencias desde config.yml.
  • Asigna puerto libre y genera credenciales.
  • docker compose up en la red del tenant.
  • Registra proxy + SSL vía la API REST de NPM.
  • Persiste en registro de texto + MariaDB.
deploy.sh
$ ./deploy.sh panaderia wordpress
[lock] flock adquirido
[deps] wordpress → mariadb (auto-deploy)
[port] asignado 8123
[cred] credenciales generadas (chmod 600)
[tpl]  plantillas procesadas
[up]   panaderia_net ✓ contenedores up
[npm]  proxy + SSL registrados (API)
[db]   registrado en users_db
✓ wordpress-panaderia.tensaas.es listo

10 Seguridad de acceso · SSO

Un solo login
para todo.

Authelia actúa de portero ante cada servicio mediante auth_request en NPM. Sin sesión válida, no se llega al contenedor.

  • SSO + 2FA: un acceso, todos los servicios del tenant.
  • default_policy: deny — solo pasa lo permitido.
  • Hashing Argon2id y baneo por reintentos.
flujo auth_request
GET wordpress-panaderia.tensaas.es
   ↓
NPM → auth_request /authelia
   ↓ sin sesión
302 auth.tensaas.es  # login + 2FA
   ↓ con sesión
200 → contenedor del tenant
   remote-user · remote-groups

13 Reto técnico real

El 403 fantasma
del SSO

Síntoma: todos los servicios daban 403 al abrirse… pero por HTTPS directo funcionaban. Despistaba a propósito.

  • El túnel de CF conecta al origen por HTTP, no HTTPS.
  • El redirect de login metía rd=http://… en la URL.
  • Una regla anti-SSRF de NPM bloquea ese patrón → 403.
Fix: redirigir con una named location; la URL viaja en la cabecera Location, que la regla no inspecciona.
diagnóstico
# Por HTTPS directo: bien
$ curl --resolve …:443 https://…
302 → auth.tensaas.es ✓

# Por HTTP (como el túnel): mal
$ curl -H 'Host: …' http://127.0.0.1/
403 Forbidden

# causa: rd=http:// ~ regla anti-SSRF
# de block-exploits.conf
